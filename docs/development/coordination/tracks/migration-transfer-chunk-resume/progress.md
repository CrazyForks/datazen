## Scope

Extend Data Transfer's existing table-boundary checkpoint to bounded checkpoints inside a table. A resumed plan must carry a deterministic source ordering/key contract and preserve its reviewed mapping and target identity. A checkpoint becomes durable only after the corresponding target chunk is confirmed committed. If commit or rollback acknowledgement is unknown, fail closed, fence later writes, and reject replay of the uncertain chunk until the user performs a fresh review/reconciliation path.

The initial supported live journey is PostgreSQL↔MySQL, in both directions. A driver may advertise in-table resume only when it can provide the stable ordered read contract; unsupported tables and drivers keep the existing table-boundary path with an actionable explanation.

## Acceptance

- Keyset pagination uses an exact stable unique key (including composite primary keys); no OFFSET checkpoint is used.
- The immutable plan/fingerprint binds the key order, source/target table identities, mappings, chunk size, and resume state. Changed plans or endpoints cannot consume an old checkpoint.
- Chunk commit acknowledgement precedes checkpoint persistence. Failure before commit leaves the previous checkpoint reusable; confirmed commit advances it exactly once; unknown commit/rollback outcome fences all later writes and prevents uncertain replay.
- Interruption at multiple chunk boundaries resumes without duplicate or skipped source keys, proven by exact source/target readback in isolated PostgreSQL↔MySQL WDIO journeys.
- Focused tests cover typed fingerprint distinctions, scalar/composite keyset SQL, filter parameter positions, safe page limits, opaque single-flight checkpoint claims, source digest mismatch, TTL expiry/cleanup, and confirmed-chunk outcome classification. WDIO specs include multi-boundary cancellation/resume in both directions, commit-ack-loss in both directions, and a PostgreSQL→MySQL source-mutation refusal journey. These tests are authored but not yet run; rollback-failure, concurrent-claim race, and live final-empty-page behavior still need independent verification.
- Added bounds and failure reasons are visible in the review UI; memory remains bounded by the configured chunk and documented metadata overhead.
- Changed executable production-line coverage is at least 80%; relevant Rust, driver, Vitest, TypeScript, formatting, and WDIO checks pass.

## Current implementation contract

- In-table checkpoints apply only to PostgreSQL/MySQL source and target sessions that are distinct, Data + Insert mode, an existing target table, a source and target table each advertising a consistent transactional snapshot (PostgreSQL ordinary local table with no partition or inheritance parent/child relationship, or MySQL InnoDB), and a source schema with the exact complete non-null supported PK index order. Unsupported combinations stay on the existing whole-table path; a saved row checkpoint whose contract no longer validates is invalidated/fails closed.
- Source rows are fingerprinted from the beginning on each run inside a PG `REPEATABLE READ READ ONLY` or MySQL `REPEATABLE READ WITH CONSISTENT SNAPSHOT READ ONLY` snapshot, with the same projection, filters, recordset bounds, and PK order used by the keyset copy. Page SQL has a hard `LIMIT`, uses bound values and no `OFFSET`; UI batch size is 1–500 and the effective size also respects the target bind-parameter budget.
- Every target page is its own transaction. Only acknowledged commit advances the server cursor. Commit, rollback, snapshot-close, or checkpoint-advance uncertainty fences later writes and invalidates the token. Preview plan TTL is 15 minutes; active execution has a 7-day lease and resumable checkpoints have a sliding 24-hour TTL. New plan/checkpoint issue purges expired checkpoint map entries while preserving active in-flight state.
- Resume detects any change to the selected source row set by full-scope typed digest validation. Target committed rows are **not** automatically validated against external edits while paused. The UI requires users to leave those target rows unchanged and to manually reconcile any target changes before continuing. This feature does not claim protection from concurrent writes or modifications to the target during a pause.
- Checkpoint storage is process memory. The token is usable only while this app process/session remains alive; closing/restarting the app loses the checkpoint. No durable cross-restart resume is claimed.
